# 这份说明是做什么的

这份文档把 2026-08-06 至 2026-08-07 的两项团队交付，用不依赖术语的方式说明清楚：

1. 每条线这一步到底在做什么；
2. 哪些部分已经通过；
3. 哪些问题会影响实验可信度；
4. 修改到什么程度才可以进入下一步。

这里的 `P0/P1/P2` 评价的是问题对研究结果的影响，不是评价个人能力：

- `P0`：会直接破坏实验有效性，继续实验前必须解决；
- `P1`：可以保留为草稿，但正式实验或对外使用前必须解决；
- `P2`：不阻塞当前内部工作，但公开仓库或写论文前应完善。

# 标注线：给模型回答制作人工标准答案

## 这一步在做什么

模型看完证据后，会给出 `UP/DOWN/NEUTRAL` 预测和一段理由。标注线把理由拆成一条条
claim，再判断：

- 这句话是否使用了 cutoff 后的证据；
- 真正依赖未来证据的是哪一小段话；
- 未来证据支持还是反驳这句话；
- 审计时是否应该删除相关未来证据。

这份人工判断以后会作为“标准答案”，用于检验 citation、lexical、embedding、
LLM judge 和完整 FinLeakAudit 的准确率。

本次审查对象是提交
[`be16042`](https://github.com/yixi1120/FinLeakAudit-KB/commit/be1604288c38d31b409851b380dc4c79f8f32fed)
中的 `semantic_annotations_annotator_a_v1.csv`。

## 已经通过的部分

- 79 条样本全部填写，没有缺失或重复 ID；
- 样本顺序和 blind batch 一致；
- 只读字段没有被修改；
- 标签枚举、置信度和 annotator ID 都符合格式要求；
- 可以保留为 `Annotator A` 的第一版原始标注。

## 还需要修改的部分

### P0：保护第二位标注者的独立性

协议要求 A、B 两个人在不知道对方答案的情况下独立完成同一批样本。但 A 的答案已经
进入 `main`，B 有可能看到。

处理办法：

- 先确认 B 是否看过 A 的文件；
- 如果没看过，B 只能使用原始 blind batch，并确认没有打开 A 的答案；
- 如果已经看过，应重新打乱样本或更换一位独立标注者；
- 两份答案在独立标注完成前不要放到同一个公开协作位置。

### P1：`matched_claim_span` 不能整句复制

当前 41 条 `yes` 样本全部把整个 claim 填进 `matched_claim_span`。这个字段真正需要的
是“只有未来证据才能支持的最短片段”。

例如：

```text
Claim:
Despite the earnings beat, the overall market sentiment and the historical
context of the sector indicate a downward trend.

应标出的片段：
Despite the earnings beat
```

“市场情绪”和“下跌判断”可能来自 cutoff 前证据，不能一起算成未来证据提供的内容。
所有 `yes` 样本都需要按这个原则重新检查。

### P1：记录标注是否使用了 LLM

79 条标注只使用了少量重复的 notes 模板，而且大多数置信度为 5。这不自动说明标注错误，
但必须留下 provenance：

- 是否使用 LLM 或其他 Agent 辅助；
- LLM 生成了哪些字段；
- 人工是否逐条阅读并确认；
- 标注期间是否查看过 coordinator key、模型名称或实验结果。

如果主要由模型生成并由人复核，应写成 `AI-assisted annotation`，不能直接写成纯人工
gold labels。

### P1：现在还不是 gold labels

当前只有 A 的答案。正式人工标准答案还需要：

1. B 独立完成同一批样本；
2. 计算三分类 agreement 和 Cohen's kappa；
3. 只讨论 A、B 意见不同的样本；
4. 保留 A、B 两份原始文件；
5. 生成并冻结 adjudicated final labels；
6. 冻结后再运行自动 baselines。

## 标注线验收标准

- [ ] B 的独立性得到确认；
- [ ] 41 条 `yes` 的 matched span 已逐条缩短复核；
- [ ] annotation provenance 已记录；
- [ ] A、B 原始答案均保留；
- [ ] agreement、kappa 和 disagreement 文件已生成；
- [ ] 分歧裁决完成并冻结最终金标。

# 数据线：制作第一个真实历史时间线案例

## 这一步在做什么

数据线选择了 2024 年 CrowdStrike 全球故障事件，收集预测截止时间前后的真实文件，
并记录每份材料什么时候公开、来自哪里、是否后来修改。

要回答的核心问题是：

> 假设我们站在 2024-07-18 美股收盘时预测 CrowdStrike，检索系统是否会混入
> 2024-07-19 故障发生后才出现的材料？

本次审查对象是 `develop` 分支提交
[`506ffe3`](https://github.com/yixi1120/FinLeakAudit-KB/commit/506ffe39fcca18ddb99eab267a059b2c9a6e470d)
中的 CrowdStrike candidate corpus。

## 已经通过的部分

- 共收集 18 篇候选文档，满足每个事件建议的 8-20 篇；
- 同时包含 cutoff 前材料、cutoff 后材料和无关干扰材料；
- JSON 与 CSV 台账的 18 条记录完全一致；
- 18 个 archive path 全部存在；
- 18 个 SHA-256 与原始文件全部匹配；
- 不确定时间没有直接猜测，而是使用 `null` 并记录问题；
- 可以保留为 `natural_001` 的候选语料包。

## 还需要修改的部分

### P0：2026 年下载的网页不等于 2024 年当时的网页

部分网页在 2024 年首次发布后被修改过，当前 HTML 还包含导航、推荐文章、页脚和大量
2026 年内容。如果把整个 `archive_path` 直接交给检索器，就会把后来新增的信息提前给
模型，形成我们自己制造的泄漏。

处理办法：

- 优先寻找当时的历史存档版本；
- 普通网页只提取与目标文章对应的正文，删除导航、推荐文章、页脚和脚本；
- 为提取后的正文记录版本时间、提取方法、文件路径和 SHA-256；
- 状态页按每次更新时间拆分，某个版本只能包含当时已经公开的更新；
- 找不到历史版本时，将材料标成不适合 point-in-time 主实验，而不是把当前全文倒推回
  首次发布日期。

### P1：修正三处已确认的时间与 URL

#### Google Cloud 状态页

当前台账写的是：

```text
available_at = 2024-07-19 06:54 PDT
```

原始页面显示最早记录是：

```text
2024-07-18 23:48 PDT
```

完整页面还包含 outcome time 之后的更新，因此需要按更新时间拆分，不能把最终页面统一
记为首次版本。

#### TechCrunch

当前 `revised_at` 是 `null`，但页面元数据明确提供：

```text
dateModified = 2024-07-20T06:23:00+00:00
```

需要填写修订时间，并确认当前正文是否包含修订后才加入的内容。

#### TechTarget

原始 HTML 明确提供：

```text
datePublished = 2024-07-24T11:11Z
```

canonical URL 也应使用 `/cybersecurity/` 路径，而不是旧的 `/searchsecurity/` 路径。
JSON 和 CSV 台账需要同步修改。

### P1：补充候选语料的收集过程

目前可以证明文件真实存在，但还不能复现“为什么正好收集到这 18 篇”。需要记录：

- 使用的搜索引擎、API 或网站；
- 搜索时间和完整查询；
- 原始搜索结果顺序；
- 纳入与排除规则；
- `doc_013`、`doc_014`、`doc_017` 没有进入语料包的原因。

在补齐这些信息并运行固定检索器前，这批材料应称为“人工收集的候选语料池”，不能直接
称为真实 RAG 的自然检索结果。

### P1：需要第二位核验者

当前所有文档都由第一次收集者核验。按照数据协议，还需要另一位核验者：

- 检查全部 cutoff 后文档；
- 抽查至少 20% 的 cutoff 前文档；
- 记录核验人、核验日期、结论和分歧处理结果。

### P2：公开仓库前处理版权快照

部分来源写明没有开放内容许可证，并注明不用于再分发。私有研究仓库可以暂存这些快照，
但仓库公开前应重新检查：公开版本优先只保留 URL、哈希、元数据和允许引用的短片段，
完整版权快照放在不公开的数据存储中。
