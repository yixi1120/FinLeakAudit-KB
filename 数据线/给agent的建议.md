**给数据智能体的任务说明**

我们正在为 FinLeakAudit 补充 **7 个真实金融事件案例**。请参考现有三个合格案例的字段结构，但不要机械复制内容。每个案例必须验证“预测截止时间、未来证据发布时间、结果观察时间”的先后关系。

### 一、最重要的时间规则

每个案例必须严格满足：

```text
clean evidence 的 available_at <= prediction_date
prediction_date < leaked evidence 的 available_at < outcome_time
```

也就是：

1. `prediction_date`：模型作出预测、此后不能再获得新信息的截止时刻。
2. `leaked evidence.available_at`：未来证据首次真正向公众开放的时刻。
3. `outcome_time`：用于计算预测结果的股价观察时刻。

必须是：

```text
预测截止 → 未来消息发布 → 观察最终股价
```

缺少其中任何一个时间，或者顺序不成立，案例都不能提交。

### 二、必须避免的失败案例

#### 1. “未来证据”其实在预测前已经发布

失败案例 ASML：

```text
证据发布：2024-10-15 12:17 ET
预测截止：2024-10-15 13:30 ET
```

消息比预测截止早了 73 分钟，模型当时本来就能看到，因此不属于泄漏。

**检查要求：**

```text
leaked_evidence.available_at 必须严格晚于 prediction_date
```

不能只看日期，要比较带时区的具体时分秒。

#### 2. 证据发布时，结果窗口已经结束

失败案例 NYCB：

```text
预测截止：2024-04-29 13:30 ET
结果观察：2024-04-30 16:00 ET
消息发布：2024-05-01 07:00 ET
```

消息发布时，4 月 30 日的收盘价已经形成，不能用它解释此前的结果。

**检查要求：**

```text
leaked_evidence.available_at 必须严格早于 outcome_time
```

不要为了让案例通过，随意把真实发布时间改早。

#### 3. 盘后消息对应了同一天的收盘价

失败案例 Microsoft、Tesla：

```text
outcome_time：当天 16:00 收盘
evidence：当天收盘后发布
```

消息发布之前，当天收盘价已经确定，因此该价格不可能反映这条消息。

如果选择盘后财报，结果窗口通常应观察**下一个交易日收盘**，但必须从一开始就正确设计预测窗口，不能事后移动结果时间来迁就证据。

#### 4. 只核对“年月日”，不核对市场时段

以下情况不能当作同一种时间：

```text
盘前 06:30
盘中 13:30
收盘 16:00
盘后 16:05
电话会 17:00
```

必须使用交易所当地时区，并考虑：

- 夏令时；
- 盘前与盘后；
- 周末和节假日；
- 下一交易日，而不是简单的下一自然日。

美股一般使用 `America/New_York` 对应的 `-04:00` 或 `-05:00`，不能全年固定一个偏移量。

#### 5. 把电话会时间误当成新闻发布时间

公司可能按以下顺序发布信息：

```text
06:30 财报新闻稿
08:00 电话会议
```

真正的 `available_at` 应是公众最早能够看到该信息的时间，即 06:30，而不是电话会时间。

需要区分：

- 新闻稿发布时间；
- SEC 文件接受时间；
- 电话会开始时间；
- 媒体转载时间；
- 数据库抓取时间。

原则是采用**最早可验证的公开可用时间**。

#### 6. 智能体根据常识编造精确时间

如果网页只写了日期，不能自行生成 `08:00:00`、`16:05:00` 等精确时间。

优先使用：

1. 公司官网新闻稿；
2. SEC EDGAR 的 filing accepted timestamp；
3. PR Newswire、GlobeNewswire 等带时间的发布记录；
4. 交易所或可靠媒体的带时间页面。

如果只能验证“收盘后”，应记录为时间区间或 `after_market_close`，不能伪装成精确时间。

#### 7. 使用假链接、搜索页或不支持结论的链接

禁止：

```text
example.com
搜索结果页面
网站首页
打不开的链接
只有事件日期、没有对应内容的链接
```

每条 URL 必须实际打开，并且能够支持：

- 公司和事件确实存在；
- 证据文本中的事实；
- 发布时间或可用时间。

最好同时保存一个官方主来源和一个辅助时间来源。

#### 8. 用股价结果本身作为未来证据

不应把下面这种内容作为主要泄漏证据：

```text
“公司公布财报后股价上涨了 18%”
```

这直接泄露了预测答案。应改用事件本身：

```text
“公司公布季度收入、利润和下一季度指引”
```

股价涨跌只能用于 evaluator 计算 `outcome_label`，不能出现在 predictor 所见的证据中。

#### 9. 向预测模型暴露人工答案标签

预测模型不应看到：

```text
time = T+1
temporal_label = future
sentiment = positive
gold_label = UP
leaked_evidence
```

这些字段可以保存在完整数据中供 auditor/evaluator 使用，但构造 predictor 输入时只能提供自然文本和允许其看到的来源信息。

#### 10. 把合成证据冒充真实证据

现有三个合格案例只是**时间结构合格**，其中部分 clean evidence 仍是合成文本，不能作为 Natural Point-in-Time 数据的来源标准。

新增 7 个真实案例应尽量做到：

```text
clean evidence：真实 URL + 真实 available_at
future evidence：真实 URL + 真实 available_at
outcome：真实市场数据 + 明确计算方式
```

如果使用合成证据，必须标注为 `Controlled-Hard`，不能和真实案例混为一组。

### 三、不要为了通过检查而“修时间”

禁止以下操作：

- 把真实发布时间人为提前；
- 把预测截止时间随意移到消息发布之前；
- 把结果窗口随意延后；
- 把自然日错误写成交易日；
- 把盘后发布写成收盘前；
- 根据文件名或事件日期猜测发布时间。

如果时间关系不成立，应该**放弃该案例，重新找事件**。

### 四、推荐选择的事件

优先寻找时间边界清楚的事件：

- 盘前发布的财报，观察当天收盘；
- 盘后发布的财报，观察下一交易日收盘；
- 盘中发布的监管决定，观察当天或下一交易日收盘；
- 带 EDGAR accepted timestamp 的 8-K；
- 带精确发布时间的公司公告；
- 并购、药物审批、指引调整、重大合同等明确事件。

避免只有日期、没有时间，或者发布时间与结果窗口无法严格排序的事件。

### 五、提交前必须执行的检查

每个案例逐项回答：

```text
[ ] prediction_date 是否有明确时区？
[ ] 所有 clean evidence 是否在 prediction_date 之前可用？
[ ] future evidence 是否严格晚于 prediction_date？
[ ] future evidence 是否严格早于 outcome_time？
[ ] 如果是盘后发布，outcome 是否使用下一个交易日？
[ ] 是否核对了周末、节假日和夏令时？
[ ] URL 是否真实可打开？
[ ] URL 是否支持证据内容和发布时间？
[ ] 是否避免编造精确时间？
[ ] 证据文本是否没有直接透露之后的股价涨跌？
[ ] predictor 是否看不到 future、sentiment、gold label 等人工标签？
[ ] outcome_label 是否由明确的真实价格规则计算？
```

任何一项回答为“否”，该案例都不要提交。

最核心的一句话可以单独强调给智能体：

```text
不要先找一个著名事件再硬凑时间；必须先验证
clean_available <= cutoff < future_available < outcome_time，
验证通过后才能把它写成案例。
```
